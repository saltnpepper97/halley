# Halley 0.8.0 Release Plan

> Temporary implementation checklist. Keep this file at the repository root while the work is active, check items only after their implementation and verification are complete, and delete this file after 0.8.0 is finished.

## Release intent

Halley 0.8.0 should make the existing compositor feel like one coherent spatial workflow for an experienced Linux user encountering Halley for the first time.

The release promise is:

- **Primary goal:** the Field workflow feels coherent and understandable.
- **Release gate:** the compositor is dependable as a daily driver.
- **Default mental model:** applications open into the Field; clusters are an optional later concept.
- **Decluttering model:** manual collapse is obvious, while conservative automatic decay handles genuinely abandoned work.
- **Compatibility rule:** existing user configurations are not automatically rewritten or migrated.

## Scope lock

- [ ] Freeze nonessential Wayland protocol work until after 0.8.0.
- [ ] Add a protocol only if testing proves it is a release-blocking application or desktop compatibility requirement.
- [ ] Defer cluster implementation, refinement, and onboarding/training until after 0.8.0.
- [ ] Do not redesign or shorten the generated configuration file for this release.
- [ ] Preserve existing configs exactly; the new experience applies only when Halley generates a fresh config.
- [ ] Record deferred protocol, cluster, and larger configuration-cleanup ideas outside this plan rather than expanding 0.8.0 scope.
- [ ] Update the Unreleased changelog when the scope-facing defaults are implemented.

Cluster-specific issues discovered during stabilization should be recorded for post-0.8 work. A cluster-related crash, security issue, data-loss risk, or compositor-wide regression still blocks release, but it does not reopen general cluster feature work.

## Milestone 3 — Add the one-time Halley basics card

### First-run behavior

- [x] Show the card automatically only when Halley created a fresh config and that config reaches its first successful native session.
- [x] Do not automatically show the card for existing configs.
- [x] Do not automatically show the card in ordinary nested/Winit development sessions.
- [x] Persist dismissal in user state so the card never reappears automatically.
- [x] Allow Enter, Escape, and an obvious pointer action to dismiss it.
- [x] Add a Lift action named **Show Halley basics** so the card can always be reopened manually.
- [x] Keep manual reopening independent of the one-time automatic state.

### Card content for 0.8.0

- [x] State the mental model plainly: **Windows live on the Field. Clusters are optional named contexts you can create later.**
- [x] Show only these five essentials:
- [x] `Mod+D` — launch or search with Lift.
- [x] `Mod+Left-drag` — move a window.
- [x] `Mod+A` — arrange visible windows or restore their saved geometry.
- [x] `Mod+N` — collapse or restore a window.
- [x] `Mod+O` — see everything in Apogee.
- [x] Do not add zoom, Bearings, Trail, pinning, cluster layouts, or a multi-step tutorial to this card.
- [x] Reuse Halley's compositor-owned overlay styling and input/modal conventions rather than inventing a separate UI system.
- [x] Keep the card readable at supported output sizes and scales without obscuring the entire desktop longer than necessary.

### Verification and documentation

- [x] Unit-test first-run eligibility, persistent dismissal, and manual reopening.
- [x] Add an explicit development/test path for manually opening the card in nested Halley.
- [ ] Visually verify text, spacing, focus handling, dismissal, and pointer behavior.
- [x] Document the card and its manual Lift action in the README, overlay docs, keybind/action docs, and Lift docs.
- [x] Add the first-run card to the Unreleased changelog.

> Milestone 3 verification note: first-run eligibility, persistent dismissal,
> manual reopening, the card's five-item content scope, the overlay lifecycle,

## Milestone 4 — Make automatic decay conservative and understandable

### Defaults

- [x] Change fresh-config decay defaults to 600 seconds (10 minutes) outside the focus ring.
- [x] Change fresh-config decay defaults to 5,400 seconds (90 minutes) inside the focus ring.
- [x] Do not migrate or rewrite existing users' explicit decay values.
- [x] Apply the longer delays through newly generated configs only; preserve the existing built-in behavior for older configs that omit the decay section.

### First automatic-collapse explanation

- [x] The first time decay automatically collapses a window, show one non-modal explanation.
- [x] Use direct wording equivalent to: **<Application> was collapsed into a node. Click the node or press Mod+N to restore it.**
- [x] Show this explanation only once per user state, not once per application or session.
- [x] Do not show it for a manual `Mod+N` collapse.
- [x] Ensure the notification does not steal focus or block input.
- [x] Handle missing application titles/IDs with a clear generic fallback.

### Verification and documentation

- [x] Test the new generated values.
- [x] Test the one-shot automatic-decay notice and its persistence.
- [x] Test that manual collapse never triggers the automatic-decay explanation.
- [x] Update node/decay documentation, generated-config comments, README quick-start material, and overlay/notification documentation.
- [x] Add the decay changes to the Unreleased changelog.

> Milestone 4 verification note: the generated `decay:` values are tested
> through bootstrap's own runtime loading path (600 outside, 5,400 inside), and
> the boundaries are tested too — an existing config's explicit decay section is
> never rewritten, and a config that omits the section still parses to Halley's
> built-in 180/1,800-second delays. The explanation is an ordinary success
> notification on the existing non-modal surface: a unit test asserts it opens
> no confirmation or basics card, makes `confirmation_modal_active` false, and
> captures no key or pointer press, and it fades out on its own. Its wording,
> title/app-id/generic fallback, and the "`Untitled` is not a name" case are
> unit-tested, as are the one-shot flag's persistence across state reloads and
> its independence from the basics-card state. Automatic decay and manual
> `Mod+N` share one collapse seam, so the trigger decides: a unit test asserts a
> manual collapse never asks for the explanation, the only collapse path with
> the automatic trigger is `collapse_for_decay`, and the manual callers (keybind
> and titlebar minimize, IPC, xdg/X11 minimize) all take the manual branch. No
> native session, and therefore no pixel-level check of the notice on screen or
> of a real focus/input trace, was performed for this milestone; Milestone 6's
> smoke test covers triggering one automatic collapse and confirming the
> explanation appears exactly once without stealing focus.

## Milestone 5 — Teach one coherent daily Field loop

The documented normal path for 0.8.0 is:

> Launch freely → position and overlap naturally → arrange when the visible Field becomes messy → collapse work intentionally → retrieve it spatially → use clusters later only when deliberately configured.

### Accomplishments

- [x] Put this Field loop near the start of the README and the relevant quick-start documentation.
- [x] Describe `Mod+A` as reversible cleanup, not a persistent tiling mode.
- [x] Describe `Mod+N` and clickable nodes before explaining automatic decay.
- [x] Keep clusters out of first-run training for 0.8.0.
- [x] Avoid presenting numbered workspaces as Halley's default organization model.
- [x] Audit terminology so Field, window, node, collapse, restore, arrange, and retrieval are used consistently.
- [x] Update examples and screenshots/text references that still imply a workspace-first default.
- [x] Add documentation-facing refinements to the Unreleased changelog where user-visible.

### Retrieval roles

- [x] Document `Mod+Arrow` as nearby spatial navigation.
- [x] Document `Alt+Tab` as recent-work navigation.
- [x] Document Bearings as retrieval for offscreen spatial work.
- [x] Document Apogee as the visual inventory across monitors.
- [x] Document Lift as direct search by application, node, cluster, or action.
- [x] Preserve all five mechanisms; clarify their hierarchy instead of removing capability.
- [x] Check that help text, README tables, and individual subsystem docs agree.

> Milestone 5 changes compositor documentation and user-visible CLI help, but
> no compositor behavior or configuration defaults. Because the rebuilt
> `halleyctl` binary changes, the verified release build was installed; the live
> compositor session and active configuration were untouched. The README,
> keybind reference, generated config, and `halleyctl --help` present the shared
> five-role retrieval hierarchy in the same order. Focused subsystem docs then
> explain their own roles: `field` and `nodes` cover nearby navigation and
> restoration, `clusters` covers cluster retrieval, `bearings` and `apogee`
> cover their respective overlays, and `overlays` identifies each overlay's
> purpose. The rebuilt help output confirmed the retrieval block and reworded
> `cluster`/`bearings`/`trail` lines, including `halleyctl bearings --help` and
> `halleyctl trail --help`. The repository had no image screenshots or
> workspace-first screenshot references to update; the remaining text
> references were the generated-config comments and `examples/split-config`.
> `cargo fmt --all -- --check`, `cargo test --workspace`, and both debug and

## Milestone 8 — Reasonable 0.8.0 release gate

The release is ready when all of the following are true:

- [ ] No known reproducible crash, session-loss bug, security issue, or data-loss risk remains.
- [ ] No known reproducible regression breaks launch, focus, movement, arrangement, collapse/restore, retrieval, fullscreen, lock/unlock, or multi-monitor daily use.
- [ ] All automated gates pass on the release candidate.
- [ ] The practical core-flow smoke test passes from a clean config and state directory.
- [ ] Native multi-monitor AMD startup, DPMS wake, suspend/resume, and ordinary daily use pass.
- [ ] Complete a seven-day daily-driver stabilization window on the release candidate.
- [ ] Reset the seven-day window only for serious behavioral changes or release-blocking fixes; documentation-only and clearly cosmetic fixes do not automatically reset it.
- [ ] Minor cosmetic issues that remain are documented and do not obscure controls, lose input, or misrepresent state.
- [ ] Unreleased documentation accurately describes what ships, with no claims based only on unverified intent.
